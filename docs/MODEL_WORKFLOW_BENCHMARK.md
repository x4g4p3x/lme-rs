# Comparing mixed-model workflows

Measured results and retained raw evidence:
[15 September 2026 comparison](../benchmarks/model-workflows-2026-09-15/README.md).

This harness evaluates whether the Rust Python bindings can replace a
formula-based statsmodels random-intercept workflow without silently changing
its numerical results. It measures a reusable statistical engine, not a desktop
application or its complete reporting pipeline.

The comparison covers fitting, adjusted comparisons, repeated null-response
refits, and leave-one-subject-out fits. It does not change a production backend
or remove any dependency. A failed compatibility check is a migration blocker,
even when the candidate is faster.

## Run

Use the locally built **release** extension, as described in
[Python integration](PYTHON_INTEGRATION.md). The comparison additionally requires
statsmodels, Patsy, Pingouin, SciPy, pandas, NumPy, Arrow, and threadpoolctl. For example,
from the repository root after building the Python environment:

```sh
uv pip install --python python/.venv/Scripts/python.exe statsmodels==0.14.6 patsy==1.0.2 pingouin==0.6.1 threadpoolctl
python/.venv/Scripts/python.exe scripts/run_model_workflow_comparison.py --output benchmark-results/model-workflows-default.json
```

On Linux/macOS use `python/.venv/bin/python` instead. The harness records actual
runtime and package versions, the extension's SHA-256, the Git revision, dirty
state, and the harness hash. It does not claim a development extension is a
published wheel or that a dirty revision alone identifies its source.

With those optional dependencies installed, run the independent numerical and
failure-gate regression tests from the repository root:

```sh
python/.venv/Scripts/python.exe -m pytest python/tests/test_workflow_benchmark.py
```

A separate precision profile explicitly changes the Rust fit-control tolerance:

```sh
python/.venv/Scripts/python.exe scripts/run_model_workflow_comparison.py --blocks 3 --warmups 1 --repeats 5 --replicates 19 --lme-tolerance 1e-10 --output benchmark-results/model-workflows-precision.json
```

This setting can select a different optimization path from the default. It is
not assumed to improve every fit, and its cost is included in the measurements.
Both profiles keep statsmodels' default optimizer sequence. No results from
different settings are combined into one speed ratio.

The runner exits **2** when any case fails compatibility. It still writes the
report and retains individual worker reports next to it. A completed run with
exit 2 is evidence of an incompatibility, not a passing validation run.

## Models and data

All observations are synthetic and generated by this script. No external source
implementation or application dataset is copied into the repository.

| Case | Subjects | Visits | Covariates | Design |
|:---|---:|---:|:---|:---|
| `balanced_none` | 12 | 4 | None | Complete |
| `balanced_within` | 24 | 4 | Within-subject deviation | Complete |
| `incomplete_decomposed` | 30 | 6 | Between-subject mean and within-subject deviation | Missing later visits |
| `incomplete_baseline` | 24 | 4 | Baseline value | Missing later visits |
| `large_within` | 240 | 6 | Within-subject deviation | Missing later visits |
| `near_boundary` | 24 | 4 | Within-subject deviation | Zero generating random-intercept variance |

Each design has three between-subject levels and an ordered within-subject
factor, deliberately including labels whose chronological and alphabetical
orders differ. Both engines use sum contrasts and a per-subject random intercept.
Missing visits remain missing; the same observed rows are used by both engines.
Covariate decomposition and centering happen once, before either backend runs.
No claim about causal interpretation follows from these synthetic comparisons.

The large case measures fitting and adjusted comparisons only. Other cases also
run all subject deletions and paired refits on shared null-generated responses.
This is a targeted six-design suite, not exhaustive statistical validation.

## What protects the mathematics

1. **Same model matrix.** Compare every design column after allowing a column
   permutation. Matching dimensions or fitted values alone is insufficient.
2. **Independent likelihood.** Profile a Gaussian random-intercept likelihood
   using direct inverses of each subject's small covariance block. Search over
   the variance ratio and explicitly evaluate its zero boundary. This reference
   uses neither statsmodels nor the Rust optimizer. Analytic balanced-ANOVA
   identities, a dense covariance calculation, and response-unit/row-order
   invariance independently test the reference itself.
3. **ML and REML separately.** Check likelihoods, coefficients, variance
   components, population predictions, conditional residuals, and random effects
   for every measured fit. ML is used for nested fixed-effect comparisons.
4. **Same inference convention.** Compare asymptotic Wald standard errors,
   intervals, multi-column term tests, and Holm-adjusted within-visit comparisons.
   Do not substitute Satterthwaite or Kenward–Roger tests while claiming identical
   p-values. The comparison adapter is also checked against public contrast and
   marginal-mean APIs rather than only testing its own matrix calculations.
   Additional regression tests check factor comparisons averaged over the other
   factor, with separate Holm families, confidence intervals, and standardized
   effects. Those marginal hypotheses must not be replaced by the conditional
   within-visit hypotheses used in the timed simple-comparison workload.
5. **Same simulated responses.** Generate fresh random intercepts and residuals
   under an independent ML null fit. Give the exact response vectors to both
   engines and compare individual LRT statistics against the independent
   reference. Comparing two p-values obtained from different random streams
   would be a much weaker test.
   Regression tests also cover the two main-effect ML comparisons within the
   additive model; the timed refit workload tests the interaction.
6. **All refits count.** Record warnings, exceptions, nonconvergence, and numerical
   failures for warmups as well as timed calls. Do not discard failed calls from
   the denominator or award them a qualified speed result.
7. **Explicit tolerances.** Tolerances are defined in the script and copied into
   the report. P-values must also agree on which side of 0.05 they fall. A close
   likelihood does not excuse a failed variance or interval check.

The Rust native bootstrap is also exercised with one and two workers. Its
observed LRT, valid count, finite replicate statistics, p-value formula, and
worker-count reproducibility are checked. Its random stream differs from the
shared-response experiment; their p-values are not expected to be identical.
The small replicate count is for comparative computation, not scientific
inference or a test of long-run type-I error calibration.

The public contracts are described in the official
[MixedLM documentation](https://www.statsmodels.org/stable/generated/statsmodels.regression.mixed_linear_model.MixedLM.html)
and [result documentation](https://www.statsmodels.org/stable/generated/statsmodels.regression.mixed_linear_model.MixedLMResults.html).
Their current web versions may differ from the version pinned for a run;
the report identifies the tested installation.

## Timing boundaries

| Metric | Included | Excluded |
|:---|:---|:---|
| `cold_ml`, `cold_reml` | Formula, design conversion, model construction, optimization, returned fit | Data generation, process startup, numerical validation |
| `adjusted_comparisons` | Grid construction and conversion, model-based means, within-visit pairwise contrasts and Holm correction | Initial fit, report rendering |
| `formula_null_refits` | Both full/null formula fits for every shared response, including frame copies | Response generation, validation |
| `shared_null_refits` | Both full/null fits for every shared response using reusable designs | One-time design preparation, response generation, validation |
| `leave_one_subject_out` | Complete REML formula fit for every preselected subject deletion | Subset creation, diagnostics/report rendering, validation |

For shared-design refits, statsmodels receives already constructed fixed-effect
matrices but constructs each new response model; Rust reuses `prepare_lmer`.
The one-time setup time is reported separately. This measures the benefit of
the available reuse APIs, not equal internal implementation boundaries.
The formula-refit metric provides the comparison without design amortization.
The reference uses Pingouin for Holm correction, as many existing Python
reporting workflows do; the statistical backend remains statsmodels/Patsy.

The main metrics are sequential and set BLAS, OpenMP, Rayon, and Polars thread
environment variables to one **before runtime imports**. Loaded BLAS/OpenMP
libraries and thread counts are recorded. Native bootstrap timing is a single
diagnostic sample for each worker count, not a repeated parallel speed claim.

Each block starts an independent process per backend. Order alternates by block.
Within a process, warmups precede measurements. Ratios use paired process medians;
intervals resample whole execution blocks, not individual fits. Three blocks give
limited uncertainty resolution. Raw times and ratios remain visible on failed
cases, with `qualified: false`; they are not equivalent-result speedups.

## Adoption criteria

Require both the default and any proposed tuned configuration to be understood.
Investigate failed fits and boundary cases before selecting an optimizer or
replacing a backend. Keep the benchmark failure gate in the adoption process.

After model-level agreement, a separate integration test must compare the actual
analysis frame, selected formulas, report fields, warning behavior, cancellation,
progress callbacks, and packaged runtime on representative real datasets. A
successful numerical benchmark alone does not establish those UI and deployment
contracts. Complete report latency and memory also require measurements in the
consumer application.

Reusable factor coding, contrasts, and prepared null refits can remove custom
model plumbing. Data preparation, covariate interpretation, diagnostics, reporting,
and unrelated statistical procedures still need their own implementations.
This benchmark does not establish that an entire general-purpose statistics
dependency can be removed.
