# Benchmark refresh · 11 September 2026

[Live dashboard](https://x4g4p3x.github.io/lme-rs/benchmarks/) · [Methodology](../BENCHMARKS.md) · [Coverage](../BENCHMARK_COVERAGE.md) · [Optimizer guide](../docs/BASIN.md)

## Decision

**Keep Argmin as the default and Basin as an opt-in feature.** Basin reproduces
the measured fits and is competitive on several workloads. This workstation
comparison does not establish consistent noninferiority across the full set of
complete and prepared fits, so it does not justify changing the default.

The predeclared per-case margin is 5%: matching numerical fits and an upper
Basin/Argmin ratio interval no greater than `1.05`. An inconclusive result means
the evidence has not established that margin; it is not proof that Basin is
inherently slower. Specialized scalar searches are shared between builds, so
variation there cannot be attributed to Basin's simplex algorithm.

## Environment and provenance

Measurements use the `0.2.6-dev.0` checkout based on
[`961efad`](https://github.com/x4g4p3x/lme-rs/commit/961efad54134ed683a0b8574463f161a1596280a),
with the documentation and benchmark-tooling changes delivered alongside this
report. The numerical library and locked dependencies are unchanged from that
revision. These are explicitly recorded as measurements from a dirty working
tree, not measurements of a later publication commit.

The fair reports retain source, lockfile, executable, harness, and fixture hashes,
runtime metadata, and every measured fit's convergence, objective, and fixed
effects. Separately built Argmin/Basin executables were copied before the
balanced runs; the harness checks their reported backend. `--skip-rust-build`
therefore records that the harness reused a binary, rather than claiming that
it built it during that run.

## Sampling and interpretation

| Suite | Protocol |
|:---|:---|
| Backend comparison | All 12 cases, ABBA / BAAB / ABBA, 6 processes per backend, 3 warmups + 11 measured fits per process |
| Rust/Julia fair fits | All 12 cases with both Rust backends; 3 warmups + 11 measurements, Rust first for Argmin and Julia first for Basin |
| Criterion | Complete main suite and opt-in production suite, both backend configurations |
| External operations | All 4 Rust/R operations plus the default Python binding; 3 warmups + 11 measurements; Basin Rust operations measured separately |
| Whole scripts | All 7 examples in Rust, R, Julia, and Python; 2 warmups + 10 complete process runs |
| Phase diagnostics | All 3 supported structures; collected separately from throughput timing |

Backend ratios summarize three independent execution blocks, with 2,000
bootstrap resamples and seed `260911`. The block count is small, so the intervals
have limited precision. Displayed backend times are medians of process medians;
paired ratios need not equal the quotient of those displayed times.

Rust/Julia intervals resample timings within one process. Reversing language
order between the two backend runs helps expose drift but does not provide
independent-session uncertainty for either backend's Julia comparison.

Criterion suites run sequentially by backend. Their ratios are regression
signals, with operation-specific sampling and setup boundaries; they do not
isolate optimizer cost or replace the balanced fit comparison. Whole-script
timings include imports, interpreter startup, and Julia JIT. External operation
timings do not automatically qualify numerical equivalence across libraries.
Brief dashboard browser checks ran during the whole-script suite, after the
fit-only and Criterion measurements. Whole-script results are not used for
optimizer selection or engine speed claims.

The first R timing pass exposed a coarse-clock problem: the median Satterthwaite
call rounded to zero. That diagnostic is retained separately. The published R
reference uses batches calibrated to at least 0.2 seconds, then records eleven
batch times divided by their call counts. It includes loop overhead and extra
untimed calibration calls; it is an amortized operation measurement. The
original zero-duration result is not used as performance evidence.

## Numerical gaps in the Julia comparison

Six of twelve default-backend cases qualify for timing comparisons. Three favor
Rust (`sleepstudy_reml`, `penicillin_crossed_reml`, `pastes_nested_reml`), two
favor Julia (`crossed_20k`, `nested_10k`), and large random slopes are inconclusive.
The dashboard excludes the remaining cases from aggregate speed claims:

| Case | Why the comparison remains unqualified |
|:---|:---|
| Weighted Sleepstudy | Fixed effects agree, but reported objectives differ by about 68.0095; normalization needs reconciliation |
| Random intercept, 10k | Objectives differ by about 25.5290 and fixed effects exceed the declared tolerance |
| Random intercept, 50k | Objectives differ by about 165.5742 |
| Random intercept, 100k | Objectives differ by about 339.9929; all 11 Julia samples report unsuccessful convergence in the Argmin reference run |
| Binomial and Poisson GLMM | The harness has not established equivalent objective conventions |

No accuracy tolerance was relaxed. Prepared Rust fits reuse design work that
Julia's complete fit reconstructs; these ratios remain diagnostic. These
results do not close the repository's locked throughput commitments or change
its completion score.

The nested-prediction and 250k-row differences did not repeat. The 50k scalar-fit and

a claim about equivalent optimizer work.
